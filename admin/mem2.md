Sim mechanics learned (from reading actual bot source, confirmed ground truth)
"Mover" bot (AAH6/front-month only): every 2.5-4.5s picks new random target price (step 20-60 normal, 40-120 on ~30% "shock" chance), walks toward it every 0.2s via marketable orders sized to eat resting depth + 20% buffer — sweeps are the large-magnitude tail of this same walk mechanism, not separate behavior
Background quoter (LP) bots on piggyback instruments (AAM6/AAU6): center c = round(fair_value(AAH6) + rel), rel fixed per contract at bot startup; requotes are full cancel-all/add-all reposting the same ladder shape, fire only when rounded c crosses to a new integer value. Ladder symmetric: bid=c-offset-i, ask=c+offset+i for i in [0,levels); offset/levels/volume fixed per contract at startup (volume ~ randint(2,6))
fair_value() reference formula: falls back to mid when spread >= 2 ticks or both book-side volumes are zero, else microprice (bidask_vol + askbid_vol)/(bid_vol+ask_vol)
Taker bot: reads BBO from one randomly chosen instrument, submits to an independently chosen instrument (mismatched book pricing), aggressive/marketable pricing, size skewed small (1 + int(20*random()**2))
EDA: all three instruments show significant individual mean-reversion (half-lives ~16-36s, needs ~13-14 min cold start for significance); cross-instrument cointegration abandoned as unnecessary — hedger does independent per-instrument flattening, not cross-instrument netting
Strategy evolution (settled design)
Decided the quoter will trade every discovered instrument, and the hedger will flatten each instrument's position independently (not net exposure across correlated instruments)
Settled quoter approach: treat driver (AAH6) as unquoted signal-only; discover driver/piggyback clusters at runtime (lagged correlation + stability debounce); recover each piggyback's rel from the LP's own requote-burst ladder; quote symmetrically around c = fv(driver)+rel, fixed +/-N ticks outside the LP's max ladder reach; own order volume = LP's observed per-level volume minus 1

Rel recovery ABANDONED — pivot to new design (current, supersedes rel-recovery thread below)
Decided rel recovery is fundamentally unreliable (concurrency/latency-dependent, inconsistent convergence) and is being dropped entirely; reasoning: rel-based edge required winning a speed/timing race against LPs which isn't achievable, so pivoting from "win on speed" to "win on price accuracy and smart quoting"
New pricing approach: no longer need rel or fv(driver)+rel at all — LP's ladder is symmetric (best bid = c-offset, best ask = c+offset), so mid(best bid, best ask) read directly off the LP's own freshly-posted book equals c exactly
New trigger logic: round(fv(driver)) changing from previous iteration is a proxy "reprice imminent" flag (not exact, since it ignores rel's effect on the rounding boundary, but fires at roughly the right rate) — on trigger, immediately cancel own resting quotes on affected piggybacks and wait for the LP's fresh post
Profit mechanism for crossing clarified: a single fill at a fair price is ~zero-EV; the edge exists because the LP's fresh c reflects fv(driver) as of the moment it decided to reprice, not as of when the repost actually lands (driver keeps moving during the LP's multi-message repost latency) — crossing right after the fresh post exploits that lag, either via mark-to-market gain as the piggyback catches up or via having an immediate directional edge to unwind against. Condition for this to be worth anything: the driver's typical move during an LP's cancel-to-last-Add window must be large enough to beat fill/slippage risk — flagged as worth checking against captured data (expected edge per cross ≈ typical driver movement during that latency window)
Burst-completion detection settled: per-instrument state (best_bid/best_ask/seen_bid/seen_ask/last_msg_time), reset on LP cancel, updated on LP Add messages (filtered by LP's own sender ID only, not aggregate BBO, to avoid taker-order contamination), considered complete when quiet for a debounce window and both sides seen; debounce window to be inferred empirically from captured historical burst inter-arrival-time data
Clarified threading model: nats.c itself runs internal I/O/delivery threads (can't be made literally single-threaded), so "single-threaded" now means only one synchronization boundary exists — NATS callback thread does a minimal enqueue only, one dedicated consumer thread (mainLoop) processes everything else (parsing, state, decisions, orders) in order; all business state (LpBurstState etc.) is touched only by that one consumer thread
Distinguishes market race conditions (state changing between observation and action — inherent risk, not fixable by architecture) from software concurrency races (fixed by going single-threaded) — taker orders potentially resting during an LP's cancel/repost gap and fill-priority risk when crossing are treated as the former, not bugs to engineer around
